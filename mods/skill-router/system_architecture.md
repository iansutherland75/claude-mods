# skill-router: how it is built

## Skills (0.1)

- **Trigger.** `skill.prompt` fires for a skill run by the Skill tool and for a typed `/skill`. It decides the model there, before the skill's body reaches the model.
- **Switch.** `turn.step` rewrites `model` on each main-loop request for the rest of the turn. Subagent steps (`agentId` set) are left alone. `prompt.submit` clears the pick, so the session model comes back on the next prompt, which matches SKILL.md `model:`.
- **Why not SKILL.md `model:`.** Most skills come from vendor installers or claude.ai sync, where local edits are lost or impossible. One pin list in `hooks/logic.ts` covers every source.
- **Jev.** This uses the Decisions API (`/api/alpha/decisions`, `~typesafe/jev-latest`) with one `choice` question, not `typesafe/jev-router`. The router runs the prompt on any vendor's model, which Claude Code can't use. Options are cut to the session tier and below (down only). The gate is the picked option's probability (≥ 0.5), not Jev's `confidence`, which reads low even on clear calls. A session model that `hooks/logic.ts` doesn't rank (fable, for now) is never routed for skills. Pins still apply.
- **Key.** `$.env.get('OPENROUTER_API_KEY')` first, then `security find-generic-password -s OPENROUTER_API_KEY -w` through `$.process.run`. Only a found key is cached, and a 401 or 403 from Jev drops it, so a key rotated mid-session is read on the next call (a stale Keychain key on Gonzo logged 401s until 2026-10-22).
- **State.** The pick for the current turn is a module variable. A reload mid-turn drops it, and the turn finishes on the session model. The on/off switches and the log (the last 1,000 lines) are in `$.store` under `enabled`, `agents`, `review` and `log`.
- **Known cost.** A switch starts the new model with a cold prompt cache. The log's `in` tokens include cache reads and writes, so the cost of a switch shows up there.
- **Built and live-tested 2026-10-21** on Claude Code 2.1.302 with headless `--plugin-dir` runs. A pin moved Sonnet to Haiku. On the Jev path, Jev picked Haiku for `claude-api` at p 0.99 in 398 ms, for $0.000017.

## Agents, conductor and review (0.2)

- **Agent routing.** `agent.spawn` fires once per subagent, before its model is resolved, with the agent type, description, full brief and `parentModel`. `decideAgent` in `hooks/logic.ts` skips forks (model ignored), resumes (model fixed), workflow agents (placeholder prompt), teammates, `claude-code-guide` and `statusline-setup`. It pins `skill-router:final-review` to `fable`. A model the session named itself is kept but held to the session tier. Everything else goes to Jev with agent criteria. A sure pick sets `model` even when it matches the session, because an unset model lets the agent's own definition decide.
- **Fable for agents.** For agent routing Fable ranks above Opus, so a Fable session offers Jev all three tiers. Jev is never offered Fable. Skill routing on a Fable session is unchanged (never routed).
- **No cold-cache penalty.** A subagent starts with an empty context on any model, so agent routing doesn't pay the cost a skill switch does.
- **Conductor rules.** `hooks/conductor.ts`, given as `additionalContext` by `classic.SessionStart` on `startup`, `clear` and `compact`. Not on `resume` or `fork`: those carry the transcript and the rules with it, and adding them again doubled them (seen live 2026-10-21). Not when `agent_id` is set. `prompt.compose` was rejected because its input has no `agentId`, so the rules could reach subagents.
- **Review gate.** `tool.call` (every tool, after `next`) marks real work when Edit, Write, NotebookEdit or an Artifact publish succeeds, in the main loop or a subagent. A successful `agent.spawn` of the reviewer marks the review. `classic.Stop` runs `stopDecision`: block with `REVIEW_ASK` when there was work and no review since it. It lets the turn end when review is off, when `stop_hook_active` is true (logged as `review skipped`, so one forced review per prompt at most), or when `background_tasks` is not empty. `prompt.submit` clears both marks. Bash writes are not seen: a read and a write look the same from here.
- **Reviewer.** `agents/final-review.md`, registered as `skill-router:final-review`, `model: fable`, tools Read, Grep, Glob, Bash (told to read only). The first line of its answer is `PASS` or `FIX`; `verdictOf` reads it into the log.
- **Log.** Entries carry `kind` (`skill`, `agent`, `review`; absent on 0.1 lines, read as `skill`). An agent's line is written at spawn with its `agentId`; its `turn.complete` adds tokens, time and the review verdict. Log writes go through one queue (`serial`) because parallel spawns would otherwise read and write over each other.
- **Built and live-tested 2026-10-21** on Claude Code 2.1.302 with headless `--plugin-dir` runs on Sonnet. Explore went to Haiku (p 1.00, 374 ms). An edit turn was blocked until the reviewer ran on `claude-fable-5-1` (PASS, 30 s, 23k tokens in). A question turn ended with no review. The rules were in context at startup and after `/compact`.

## Agents band and pane (0.3)

- **State.** Two atoms, typed in `types/index.d.ts`. `skill-router.agents` holds an `AgentCard` per subagent. `skill-router.view` mirrors the `view` setting in `$.store` (`band`, the default, `pane` or `off`), loaded at `session.start`, so `/skill-router view` redraws at once. Session-scoped, so a new session starts empty and a reload keeps the cards. A card's `id` is the start time plus the mod's own counter, not `tool_use_id`, because a workflow's agents share one. The time keeps ids apart after a reload resets the counter.
- **Every spawn gets a card**, routed or not. `agent.spawn` adds it as `routing` before `routeAgent`, fills in the Jev fields after, and moves it to `running` with `next(e)`'s resolved `model` and `agentId`, or to `denied`. Workflow agents and forks do fire `agent.spawn`, so they show up as `kept` with the reason. A spawn with no `agentId` (a workflow's remote agent) is marked `done` at once, since no later event names it.
- **Progress.** `tool.call` with an `agentId` adds one (not awaited, so the pane never holds up a call) to that card's `tools` and sets `lastTool`. An `agentId` no card holds (compaction and memory forks) is ignored. The bar is `tools / expected`, held at 90% until `turn.complete` for that `agentId` marks it `done` (or `stopped` when aborted, refused or errored). `expected` is the mean `toolCalls` of the last 20 logged runs of that agent type, or a first guess (Explore and Plan 15, general-purpose 20, the reviewer 12) until three are logged. `toolCalls` is new on `LogEntry` in 0.3, so the average starts from zero history.
- **Redraws.** No throttle code. A write to the atom redraws the pane at the engine's redraw rate.
- **Band.** The default view. A `ui.render` hook on `AbovePrompt` draws while there are cards and the view is `band`; otherwise, or while a survey holds the band, it returns `next(e)`. Live agents come first, then the latest finished ones, up to six rows; the heading counts the rest and points to the pane. The row leaves out Jev's line, which needs a card's width. The engine gives the band its own `[-]` to collapse it.
- **Pane.** Opens on each new card only under `view pane`. `/skill-router pane` opens it at any view. An unasked open is only placed when the surface is wide enough; when it isn't, one toast a session says to run `/skill-router pane`, which is the asked path and is placed at any width.
- **Clearing.** A typed `prompt.submit` drops finished cards and closes the pane when none are left running. A slash command doesn't, or `/skill-router pane` would open on an empty pane.
- **Drawing.** `hooks/pane.ts`. The band is one SVG on desktop (`bandSvg`) and a text line an agent on the terminal (`bandLine`). Desktop and the other app surfaces get one SVG per pane card sized in pixels (13 per reported column), as work-report does, because their text is proportional. A running bar has an SMIL opacity pulse. The terminal gets four text rows per card with a `█░` bar. All card text comes from the pure functions in `hooks/logic.ts` (`routeText`, `statusText`, `progressOf`, `colorOf`), which the tests cover.
- **Pane trouble never blocks work.** Every card write goes through `quietly`, so a failed write loses one update and the agent or tool call carries on.
